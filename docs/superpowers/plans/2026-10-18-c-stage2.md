## 二、全局约束与当前事实

### 全局约束

- 使用既有三层架构，不增加 DAO、Redis、内部 HTTP 接口或第二套事件框架。
- 正式业务写入由所属模块 Service 负责；测试准备数据不能变成生产绕行入口。
- 对外 ID 继续使用十进制字符串，保留既有字段、错误码及版本语义。
- 认证、功能权限、管理员资格、对象范围、可授权角色分别检查；不能互相替代。
- 不使用跨请求允许缓存；等待锁结束后必须复核当前事实，不能把旧快照当成最新权限。
- 业务事实、签名、关键审计与相应成功结果必须原子提交。D 内部签名/业务审计参加调用方事务。
- 外部事件接收/失败记录和批量逐项事务有各自既定边界；“同事务”不等于把整批或事件全部阶段放入一个事务。
- 不伪造管理员执行 HR/OA，不把 `TrustedEventContext` 的构造本身当作认证成功。
- 不改写历史授权来满足现时规则，不自动恢复已撤销来源，不因验签失败给旧数据自动补签。
- 密钥、密码、完整 JWT、真实人员明文和本地配置不进入源码、审计或测试报告。
- 现有库只执行核对后的增量迁移，不重跑空库建表，不删除数据卷代替迁移。
- 新表、新字段、新 HTTP 接口和公共契约变化必须按团队流程协调，不能用个人实现决定冒充已确认设计。

### 初始基线中已经存在的能力（C2-01 变更见上方交接）

- C 已有管理员/清单、单人授予与来源回收、异步批量基础；逐项当前资格检查已有实现和第一阶段测试，第二阶段应扩展真实依赖与恢复场景，不重复开发。
- `AdminIntegrationConfiguration`、`GrantIntegrationConfiguration` 仍提供缺失依赖时的拒绝实现；不能仅因 D 代码合并就宣称 C 已接通。
- D 已提供 `PermissionService.requireFunction`、`DataSignatureService.sign/verify`、`AuditService.change` 等真实能力；服务请求认证、防重放仍属 D 第二阶段。
- A 已有 `ExternalEventService` 和 `HrCollaboration` 接点；C 的 HR 实现尚缺。A 的接口是当前接入线索，不代表所有跨模块细节均已冻结。
- `AdminRules` 当前没有合并部门生命周期判断。A 文档中 Task12 旧实现已被 Task20 更正，不能按历史段落认定 C 已完成此功能。
- `BatchWorker` 目前没有启动扫描或自动重试；同幂等键重发只查询已有任务，不是恢复操作。
- GR04 和 OA01 尚未由 C 实现。
