# 姓名搜索：沿用团队现有数据库（Task18）

依据团队 `docs/contracts/04-database-design.md` 的23表、`02-api-spec.md` US01 的管理范围/允许后解密/手机号掩码要求，以及用户2026-10-17确认的无新增表方案实施。Task17 两表是我方额外设计，已撤下；自行补写的旧说明不能证明团队批准。本次不增加表、数据库字段、索引、密钥、HTTP接口或业务规则。

## 现行处理

US01 沿用原 JWT/当前会话、D 功能权限、C M5 当前范围及锁序。在同一个 REPEATABLE READ 事务内，先以 SQL 约束管理范围与部门/状态/来源交集。非空 keyword 按稳定用户 ID 分批读取，每批最多200人；每个候选先验签，再解密姓名，在内存中按 strip + NFC、大小写/重音敏感的字面连续子串匹配。完整词、单字、中间片段和 Unicode 补充平面字符均不拆分代理对。用户名/SG号仍由原 MySQL LOCATE 比较，完整规范化手机号仍通过已有 HMAC精确比较；SQL只投影临时命中标志，不新增列。同一用户 OR 命中一次。

完整遍历候选并累计精确 total，只保留目标页的展示记录，按ID稳定排序；不能凑满一页就停止、不能先分页再过滤或截断扫描。范围外资料不读取/不解密；范围内任一候选验签或姓名解密失败则整次失败，包含非目标页及未命中资料，不能忽略损坏记录返回部分结果。手机号沿用掩码及已有完整性检查。无 keyword 时保留原 SQL count/list 分页，不额外扫描姓名。

US03和HR02继续在原事务写姓名密文及原签名/审计，新建或HR改名随后即可搜索；不需要新DDL、索引回填或专用密钥。姓名明文不写日志、磁盘或跨请求缓存。旧索引组件、维护入口、专用配置与20261017迁移均删除；空库schema及Compose健康条件保持23表、18触发器、49CHECK。Task20仅保留已确认的部门合并迁移，事件认领列及迁移已撤回；C五文件恢复main，A按C原公共方法适配，现行说明见[接入记录](task12-c-integration.md)。

`UserAccount.identifierMatched` 仅为当前SQL查询的临时投影，不持久化、不进入HTTP响应，也不属于D规范身份签名载荷；沿用临时投影排除规则。真实D须对原身份事实按同一事务一致视图验签，当前测试使用明确身份字段清单，未新增D接口或签名字段。

## 能满足与限制

支持姓名包含、权限/筛选交集、完整统计及分页、旧账号即时搜索，无数据库设计扩展。非空关键词每次验签和解密次数随范围内候选人数线性增长，SQL过滤和排序开销另计；每请求均需全扫描候选姓名，即使查询第一页，持有原事务和管理锁的时间也会增长。200仅是内部单批数量，不是结果或扫描上限；30秒原事务超时不变，超时明确失败。未完成大规模性能验收，不能宣称达到20ms/50ms目标。不同请求间并发变动仍可能导致分页变化；同一次查询的total与items来自同一事务视图。

真实D签名、功能、解密协作及真实C HR回收尚待团队接入；生产默认拒绝保持。测试D/SMS替身不能作为完整跨模块联调证据。原23表以外任何确需新增的设计，须先说明必要性/影响，由用户向组长请求，未经确认不实施。
