# 6. 事务、签名与日志

事务保证“修改角色、更新签名、保存日志”一起成功或一起回滚。源码入口为各 Service 的 @Transactional。

## 简单并发规则

修改用户角色锁用户一行，修改角色菜单锁角色一行，修改菜单 API 锁菜单一行。第二次保存等待第一次提交后，再读取和验证最新目标。

没有全表管理锁，没有业务修订号，也不检测旧页面。最终结果是后保存请求提交的完整集合，不能是两次请求混合出来的集合。

调用另一个 Service 的 public 方法才能经过 Spring 事务代理；同类中 this 调用不会新建代理事务。批量服务正是调用 GrantService 的代理，使每个人独立提交。

## 签名

SignatureService 使用固定格式 Ed25519。用户签名同时覆盖身份字段、手机号、范围、会话版本及角色 ID 集合；角色覆盖菜单集合；菜单覆盖 API 集合。应用、API、部门也保护关键字段。

先验证旧数据，再修改和签名。直接删一条用户角色关联而不更新用户签名，同样会被发现。不能在验签失败后自动重新签名。

只有固定一对密钥和一种格式，不学习密钥轮换、日志封印、证据图等外围机制。

## 日志

操作记录保存对象、结果、原因、时间、操作者及当时部门。鉴权保存允许/拒绝；不保存完整密码、JWT 或服务密钥。

登录失败需要先提交失败日志，再由 Controller 返回 401，否则在事务内直接抛异常可能把失败日志一起回滚。

练习：为什么只对手机号签名、却不对用户角色集合签名，无法发现别人直接修改数据库授权？
