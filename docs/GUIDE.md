# 功能与演示说明

## 一、实现边界

- 一个 Spring Boot 后端、一个 Vue 管理前端、一套 MySQL 数据库。
- Controller 接收参数；Service 实现业务步骤与事务；Mapper 执行 SQL。沿用现有六功能模块和数据库结构。
- 不新增角色继承、显式拒绝、角色等级表、微服务、消息队列或 Redis。
- 简洁以能顺着方法读懂业务为准。签名、审计、事务、来源精确回收是详细设计已有要求，不能用删除这些检查来换取行数减少。
- 只有多处实际重复的处理才提取公共方法或服务，不为每个 Service 增加接口、实现类或通用策略框架。

## 二、统一权限规则

### 功能权限：RBAC0

用户关联角色，角色关联菜单，菜单关联 API。多个有效角色的权限取并集；用户不直接获得菜单或 API。角色不继承其他角色。

`PermissionService` 从当前数据库计算权限。JWT 证明登录身份；账号状态、会话版本、注销记录和当前授权仍需检查。回收最后一个授权来源后，下次请求应拒绝；保留其他有效来源时，角色仍然有效。

### 管理资格：与功能权限同时校验

一个管理操作需要同时满足：当前会话有效、具备该操作功能权限、管理员任命有效、目标在可管理范围内。资源与角色维护还要求一级管理员。

2026-10-21 经项目负责人确认，普通业务角色和管理功能角色使用同一套可委派规则：

1. 一级管理员可以授予有效的普通业务角色或管理角色。
2. 下级管理员只能授予上级明确放入其可授权清单的角色。
3. 向下委派清单时，目标等级必须更低且处于操作者管理范围内，操作者自己也必须有资格委派该角色。
4. 获得管理角色不会自动产生管理员任命，也不会提高管理等级。
5. 超级角色不能通过普通角色创建、授予或委派入口操作。

这些规则集中在 `AdminRules.checkRole` 等现有方法中。已删除“等待其他模块提供管理角色规则”的 `ManagementRoles` 接口及布尔资格参数；不再保留永久拒绝所有管理角色的阶段占位实现。

## 三、按功能阅读代码

| 功能 | 先读的 Service | 需要理解的问题 |
| --- | --- | --- |
| 登录与账号 | `auth/AuthService`、`user/UserService` | 密码如何校验，JWT 如何产生，注销为何能让旧令牌失效 |
| 组织与人事 | `department/DepartmentService`、`hr/HrService` | 人事事件如何认证、去重、更新组织和回收授权 |
| 应用与权限资源 | `resource/ResourceService` | 应用、菜单、API 和映射如何维护 |
| 角色与授权 | `role/RoleService`、`grant/GrantService`、`grant/GrantOperations` | 角色定义与授予有何区别，多来源为何不能直接删除用户角色 |
| 管理员与范围 | `admin/AdminService`、`AdminPolicyService`、`AdminRules` | 功能权限、管理员资格、部门范围如何共同生效 |
| 在线鉴权 | `permission/PermissionService` | 如何计算菜单并集和 API 访问结果 |

公共处理：`DataSignatureService` 负责事实签名与验签；`AuditService` 负责审计；`ExternalEventService` 负责 HR/OA 事件记录；`ManagementAccessService` 统一资源和角色入口的会话、管理员及功能检查。

## 四、三条必须讲清楚的流程

### 登录和访问

登录 Controller → `AuthService.login` → 查询账号、校验签名和密码 → 生成 JWT、记录登录审计。访问时再通过 `PermissionService.currentUser` 检查当前会话，通过 `requireFunction` 或 `check` 检查当前功能权限。

### 管理员授予与回收

`GrantController` → `GrantService` → `GrantOperations` → `AdminPolicyService` 校验范围与角色资格 → 检查功能权限和授权版本 → 修改授权来源与有效关系 → 更新版本、签名、审计 → 同一事务提交。

只回收指定来源。如果另一个岗位或人工授权来源还有效，用户的对应角色继续有效。管理员任命和用户角色是不同事实，不能互相代替。

### 资源或角色维护

Controller → 业务 Service → `ManagementAccessService` → 业务规则校验 → 修改前验签 → Mapper 写入 → 修改后签名 → 审计 → 事务提交。

写入取得管理锁后，需要重新读取当前会话，避免在等待锁时已经注销的令牌继续操作。这个细节由公共服务封装，资源和角色 Service 不再重复实现。

## 减少冗余的具体做法

1. `IdUtils.parse` 是 ID 文本校验的单一实现。业务类直接使用它，删除六处原有方法，历史查询仅保留“可选参数为 null”的转换。
2. 管理范围集合由 `AdminPolicyService.managedScope` 计算。`AccountManagementPolicy` 只保留账号模块所需的加锁和错误码适配，不再依赖另一份组织 Mapper、签名服务和链遍历。
3. 部门树索引每次查询建立一次；不在每个节点的循环内重复建立。
4. 三个自定义弹窗共用 `dialogKeys`。每个调用方仍自行决定忙碌时能否关闭，没有引入弹窗框架。
5. 正式前端使用统一排版；保留简单 Vue 组件、现有请求封装和列表方法。行数增加是因为展开原来的单行模板，不是增加业务功能。
6. 不为每个 Service 新建接口/实现类；现有跨模块签名和审计适配仍承载事实转换及事务职责，不按类名或行数机械删除。

## 有意保留的复杂度与限制

- 签名、可信审计、授权来源、事件幂等、批量恢复和事务一致性来自详细设计。删除这些不是等价重构。
- 当前管理写入采用较宽的固定加锁顺序，部分账号查询也复用该协议。这是并发正确性与性能的现有取舍；本轮没有未经并发验证便删锁或改成缓存。
- 历史查询为精确总数逐批验签、过滤候选记录，前端多选历史还会读取多页。可进一步优化查询投影，但涉及留存证据与范围语义，不能简单改成“只验当前页”来提速。
- 演示初始化、超级用户恢复、真实部署与正式性能指标不在本轮已完成范围。

## 本轮按最终项目重构

不保留只为两阶段开发而存在的占位装配。账号与部门需要真实签名、审计和管理模块；缺少必需依赖的局部应用拒绝启动。HR 的不可用占位实现与 API/OA 的备用拒绝装配已归档，正式应用使用真实实现。外部请求不合法仍由真实服务认证拒绝。

- 账号：list 只表达校验、授权、查询、审计；普通分页与加密姓名搜索分开。创建临时账号的数据组装独立，详情与状态变更共用范围内用户检查。
- 认证：login 负责事务边界，authenticate 负责凭据验证；新密码校验与保存分开。错误密码、错误验证码的计数必须先提交再抛错，因此保留 Outcome，不机械改成事务内抛异常。
- 组织：统一读取并验证组织，树节点展示与业务流程分开，部门变更共用持久化循环；合并、冻结仍保留各自规则。
- 资源与角色：ID 集合去重与正数校验只有一份；前后变化的审计证据由现有 AuditService 统一组装，不新增通用 CRUD 框架。
- 在线权限：授权来源一致性、角色菜单并集从 calculate 中拆成有明确含义的方法；仍逐次验签，不引入缓存或角色继承。
- 全部生产 Java 使用统一排版，展开密集语句；移除 40 个只有“后续逐步实现”说明的 package-info 占位文件。

按用途重命名：AccountSecurity、AccountSecurityService、ManagementDataSecurityService、AccountManagementPolicy、DepartmentAccessService。测试名也改为账号认证、账号管理、账号完整性、HR 完整性、资源角色、权限审计等功能名称，不再要求先理解 A/B/C/D 分工。

### 学生阅读与答辩顺序

1. 从 Controller 找一个接口，检查请求 DTO 的字段与校验。
2. 在 Service 找公开方法，按“校验 → 权限/范围 → 业务修改 → 签名/审计”阅读。
3. 查看对应 Mapper/XML，解释修改了哪些表。
4. 找同名功能测试，先看正常场景，再看拒绝和回滚。

重点读 UserService.list、AuthService.login/changePassword、DepartmentService.freeze、RoleService.replaceRoleMenus、GrantService.grant/revoke、PermissionService.ownMenus。保留事务和锁，是为了业务、版本、签名和审计共同成功；保留授权来源，是为了调岗不误撤人工授予的角色。这些是业务要求，不是可以直接删去的重复代码。
