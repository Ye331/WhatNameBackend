# 第一阶段 API 手动用例清单

依据组内共享的《详细设计和 API 设计 v3》（`02_API接口设计规范.md`、`03_OpenAPI_3.0_候选契约.yaml`）和仓库 `DEVELOPMENT_PLAN.md`；设计文件位于仓库外，不随本 PR 提交。下列路径均加前缀 `/api/v1`。本清单用于逐模块验收；**待执行不等于通过**，Controller 有路由也不等于业务可用。

当前仓库已有 `src/test` 中的虚构账号、资源和授权夹具，可用于第一阶段独立自动化测试；它们不会导入个人开发库。`db/` 与本地配置脚本只建表并提供部门开发数据，未提供可登录超级账号的初始化入口。C/D 等生产适配仍会在必要认证、功能判断或签名缺失时拒绝。因此下面的业务 HTTP 成功用例需等团队完成受控初始化与真实接入后再验收；**不要求测试同学索取真实用户资料、密码或私钥**。

## 执行前的数据与凭据

| 对象 | 当前本地状态 | 成功用例所需的受控数据 |
|---|---|---|
| 部门 | 111 条 `DEV-DEPT-*` 开发数据 | 可用于层级读取；正式鉴权链路还需团队按设计签署的组织数据 |
| 应用、菜单、API 资源 | 各 0 | 至少一套管理应用和演示业务应用资源，记录每个菜单的 API 映射 |
| 用户、角色 | 各 0 | 可登录管理员、普通用户、范围外用户；有效角色与授权来源 |
| 服务凭据 | 尚未验收 | HR、OA、业务服务分别提供受控身份及签名方法；凭据不要写入仓库或测试报告 |
| 前端按钮 | 后端无独立按钮表，尚未统计 | 前端提供按钮清单及按钮到 API 的调用关系；不要把按钮数直接算作 `sys_menu` 行数 |

应用、账号、授权与签名数据应由负责模块的正式入口或团队批准的受控初始化流程准备，不直接往业务表插入伪造成功数据。老师的测试数据到来后，记录来源、数量、导入时间与版本。

## 已执行的基础 HTTP 用例

| 用例 | 操作 | 预期与实际 | 结果 |
|---|---|---|---|
| S01 | `GET /system/ping` | HTTP 200，`data.status=UP` | 通过 |
| S02 | `GET /system/database` | HTTP 200，`data.status=UP` | 通过 |
| S03 | 不带 JWT 请求 `GET /departments` | HTTP 401，`code=INVALID_TOKEN` | 通过 |

三项响应的 `X-Request-Id` 均与响应体 `requestId` 一致。另有部门 Mapper 的 3 项真实 MySQL 读取测试通过；详见 [测试记录](STAGE1_TEST_RECORD.md)。

A、C、D 及新增 B 模块隔离数据库测试分别通过 106、51、16、3 项。B 的 3 项验证服务层和真实 Mapper；**正式 HTTP 的未登录访问控制检查发现 S1-SEC-01，见测试记录，B 模块当前不通过验收。**

## 待执行的逐模块用例

每项记录请求时间、接口编号、脱敏请求、HTTP 状态、业务码、关键响应字段及数据库证据。密码、完整 JWT、短信码、私钥和个人敏感信息不进入记录。

| 用例 | 设计接口 | 数据准备与操作 | 通过标准 | 当前状态 |
|---|---|---|---|---|
| A01 登录 | AU01 `POST /auth/login` | 已设密码的有效账号；分别提交正确与错误密码 | 正确凭据返回 accessToken；错误凭据返回 401 且不泄露账号是否存在 | 待账号与签名数据 |
| A02 用户查询 | US01 `GET /users`、US02 `GET /users/{userId}` | 有管理范围的管理员查询范围内用户，再查范围外用户 | 仅返回有权查看的数据；姓名/手机号按契约处理，范围外不得泄露 | 待管理员和用户数据 |
| A03 临时账号 | US03 `POST /users/temporary` | 合法管理员创建临时账号，再用 US02 查询 | 返回字符串 ID；`sys_user` 新增且来源、状态、审计一致 | 待正式写入链路 |
| A04 组织查询 | DP01 `GET /departments`、DP02 `GET /departments/{deptId}/users` | 管理员查询根、分支和子部门 | 只显示管理范围内层级；下属人员与 `includeDescendants` 一致 | 待可验证的签名组织和管理员数据 |
| A05 HR 基础同步 | HR01、HR02 | 用可信 HR 身份提交部门/员工新版本 | 返回 `processingStatus=APPLIED`；部门、员工与事件记录一致。重复、乱序另列第二阶段专项 | 待可信 HR 接入与测试事件 |
| B01 应用登记 | RE02 `POST /applications`、RE01 `GET /applications` | 一级管理员创建测试应用并查询 | 200；应用编码唯一，数据库应用记录与响应一致 | 服务层持久化通过；HTTP 无凭据可查询及创建，S1-SEC-01，验收不通过 |
| B02 菜单树 | RE05 `POST /applications/{appId}/menus`、RE04 `GET /applications/{appId}/menus` | 创建 1 个目录、2 个权限菜单并查询 | 目录和菜单类型、父子关系、状态正确；目录不可直接授权或关联 API | 服务层已验证 1 个目录、1 个权限菜单及防环；完整用例和正式 HTTP 待验收 |
| B03 API 映射 | RE08、RE07、RE10、RE11 | 登记至少 2 个不同方法/路径的 API，并关联到一个权限菜单 | 查询返回准确映射数；旧 `expectedVersion` 更新返回 409；目录不能关联 API | 服务层已验证路径冲突、跨应用拒绝、映射及旧版本拒绝；HTTP 状态码待验收 |
| B04 角色菜单 | RL02、RL05、RL06 | 创建角色，将权限菜单关联到角色后查询 | 返回准确菜单集合及修订号；旧版本替换被拒绝 | 服务层映射及旧版本拒绝通过；HTTP 无凭据可创建角色，S1-SEC-01，验收不通过 |
| C01 管理范围 | AD02、AD04、AD05、AD06 | 任命下级管理员并设置可授权角色清单 | 等级、管理根、可授权清单正确；越范围或旧版本操作被拒绝 | 待管理员及真实身份接入 |
| C02 授权来源 | GR01、US05、GR05 | 给同一用户和角色登记两份独立有效来源 | 用户角色有效，来源数为 2，授权版本变化与数据库一致 | 待受控账号、角色及签名审计 |
| C03 精确回收 | GR02、US05、GR05 | 只回收 C02 的一份来源，再回收最后一份 | 首次仍有角色；最后一份回收后角色失效；保留来源历史 | 待 C02 成功 |
| C04 批量任务 | GR03、GR06 | 用 `Idempotency-Key` 提交小批量并查询结果 | 首次持久接收返回 202；每项有状态；同键同内容不重复执行 | 待受控多用户数据 |
| D01 当前菜单 | AU02 `GET /auth/menus` | 已授权与未授权用户分别查询同一应用 | 只返回有效菜单；补全的祖先仅用于显示，不扩大 API 权限 | 待预置权限及正式集成 |
| D02 API 决策 | AU03 `POST /auth/check` | 可信业务服务携带有效用户 JWT，请求已授权与未授权 API | 只有匹配应用、方法、路径且已授权时 `data.allowed=true`；拒绝也留鉴权审计 | 待可信服务身份接入 |
| D03 审计查询 | LG01—LG04 | 管理员查询操作、授权决策、登录日志及证据 | 仅返回管理范围内记录，留存证据可验签且不泄露敏感值 | 待签名、审计与范围接入 |

第一阶段计划还有最小联调链：**登录 → 授权 → 菜单 → API 允许 → 回收 → API 拒绝**。A01、C02、D01、D02、C03 都成功后才执行并记录这条链；不能用各模块的测试替身结果替代真实联调。

## 菜单、按钮、API 数量登记

老师要求的数量以**实际测试数据**为准，不预填虚构数字。资源准备完成后填写：应用数、目录数、权限菜单数、前端按钮数、API 资源数，以及每个权限菜单关联的 API 数。数据库可用 `sys_application`、`sys_menu`、`sys_api`、`sys_menu_api` 统计；按钮数及按钮触发的 API 由前端页面清单核对。每次数据变更后更新统计时间和版本。
