## 规则与边界

| 情况 | 当前处理 |
|---|---|
| 账号或管理根所在祖先被冻结 | 管理操作、新任命、新授权拒绝；合格上级仍能定位该部门以便解冻/撤任命。冻结本身不永久撤任命 |
| 账号部门或管理根位于已合并源/其祖先已合并 | 管理资格拒绝；合并源不能承接新任命或新授权；历史对象仍可被合格上级查看、撤任命 |
| 合并令原根失效，或管理员本人归属改变 | 任命置为撤销，保留原等级、原管理根及历史；不把根自动映射到合并目标 |
| 原部门范围增加子树、新部门，或接收原范围外人员 | 撤销受影响的部门管理员任命，等待有资格上级显式重任命；一级管理员原有集团范围不因新增部门自动失效 |
| 范围单纯缩小且根及本人归属仍有效 | 可保留任命；失去范围依据的委派清单项收缩 |
| 委派提供者/接收者任命需重审 | 删除失效清单项，沿 `(configured_by, role_id)` 精确递归收缩；独立由其他上级配置的角色不被无差别删除 |
| 重任命 | 沿用现有任命入口和功能、等级、范围检查；清单重新配置，不自动恢复过去清单或已撤销来源 |
| 历史角色关系和授权来源 | 组织重审不改 `sys_user_role`、`sys_user_role_source` 或 `grant_revision`；不等于 HR 回收 |

失效任命的状态限制、清单收缩、版本推进、管理员双签名、关键审计在同一事务内完成，对外不会暴露已扩大的临时管理资格。每个变更管理员的 `delegable_revision` 在一次重审内只前进一次。失败时整笔业务回滚。

`AdminData.Department` 读取既有 `merged_into_dept_id`；XML 使用显式四参数映射，兼容既有三参数 Java 构造。没有数据库迁移、新等级字段、普通超级用户接口或外部 HTTP 契约变更。

### 管理角色及人工回收

现有 B 模型只有 `role_type`，契约只描述“符合等级规则”，尚无获批的等级映射。**用户已明确确认：暂无规则，继续默认拒绝并记录依赖。** `AdminPorts.ManagementRoles.canDelegate` 保留拒绝实现；不能从角色名、角色代码或菜单内容猜等级。管理功能角色不会自动产生 M5 任命。超级角色始终禁止普通授权。

人工来源回收沿用现行条件：有效操作者、对象范围、功能权限、角色类型/启用状态、当前可授权清单全部满足。因此停用角色或清单外角色不能借人工接口回收。本次不放宽该规则。C2-03 的可信 HR 强制清理必须独立于这些人工条件，特别不能因角色停用或操作者清单缺项留下离职授权；该入口尚未实现。

## A/C 内部组织协作

既有 `organizationChanged(Set<Long>, List<Map<String,Object>>)` 的参数和语义保留。为避免 A 先锁组织/用户后倒序进入 C，内部 `DepartmentCollaboration` 增加 `prepareOrganizationChange(TrustedEventContext, eventId)`；默认实现拒绝，不能悄悄跳过。A 的 sync/merge 事务回调已经前置调用它，`CBackedDepartmentCollaboration` 转交 `AdminOrganizationLifecycle`。

这属于本分支 A/C 内部协作变更；没有修改 `docs/contracts` 或声称团队外部契约已批准。其他自定义 `DepartmentCollaboration` 实现需显式支持准备阶段，不能只实现末尾回调。

调用顺序：

1. A/D 验证真实服务身份、请求范围及防重放；A `ExternalEventService` 认领并锁事件行。
2. 在 A 现有 **SERIALIZABLE** 业务事务中、组织/用户读取前调用准备：管理员 → 部门 → 角色 → 清单 → 全部用户（主键序）→ D 应用/菜单/API/映射锁。C 验证原组织、部门、用户身份、任命、清单和角色签名。
3. A 校验和修改组织、迁移人员，传入受影响部门集合及移动前用户行（`id`、`deptId`）。C 核对实际归属差量，拒绝未声明用户移动、删除部门、改账号状态或顺带修改管理员/角色/清单等混入操作。
4. C 用前后事实重审，限制任命、递归收缩清单，重签全部受影响管理员的 `ADMIN` 与 `ADMIN_DELEGABLE_ROLES`，追加 D 审计。
5. A/D 完成 `ORGANIZATION`、变化 `DEPARTMENT`、迁移人员 `USER_IDENTITY` 的最终签名及组织审计；A 写入事件 APPLIED。C 提交回调要求本次重审已完成，并验证最终事实与最终签名，随后共同提交。

准备上下文绑定事务，挂起时解绑、恢复时绑定，完成或回滚清除。缺准备、重复准备/回调、缺回调、旧隔离边界均拒绝。准备后异常不能吞掉继续提交。事务内重审之后再改变范围，即使补上有效签名，也不等同重新完成范围重审。

该流程读取和锁定全部管理员、组织和人员，以当前已有全局 M5 串行化基线保证正确性；没有验证大规模组织调整吞吐。后续若优化锁范围必须保留当前事实复核、按主键锁序和并发测试。B 全局资源写入仍需对齐“角色优先，随后资源/映射”的锁序及 D 签名，现有部分 B 接口尚未对齐。

### 审计

`ADMIN_ORG_REVIEW` 使用 D `AuditService.change`，`target_type=USER`、目标为被重审管理员、`external_event_id` 关联 A 事件；服务操作不伪装成普通管理员，`user_id` 为 NULL。证据结构为 `C_ORGANIZATION_REVIEW_V1`，包含服务来源/clientId/requestId/eventId、受影响部门、是否需重任命、管理员及其委派的变更前后事实。D 继续负责 seal 和原子追加；现有 D 元数据 `source_system` 仍为 IAM，HR 来源保留在 `origin.sourceSystem`，查询事件须结合两者。

没有管理员/清单变化时不额外制造管理员变更审计，A 的组织事件审计负责记录该组织操作。证据不记录完整 JWT、人员密文、密码、密钥或原始外部请求。

## 超级用户初始化、恢复及自管资源协作责任

以下是 C2-07 要求的责任划分和验收条件，**不是已交付通道或团队已完成签收**。

| 责任方 | 交付责任 | 联合验收必须证明 |
|---|---|---|
| A | 受控初始化/紧急恢复编排、独立身份凭据保护、账号密码初始化、会话失效与恢复后的身份最终签名接点 | 没有可用默认密码或普通接口创建超级用户；恢复后旧会话不能继续使用；失败回滚 |
| B | 本系统 IAM 自管应用、菜单、真实 API 路由及映射、管理/超级角色定义；提交可判定且获批的管理角色等级资格规则 | 超级角色不能经普通 RL/GR 接口创建/分配；自管资源不靠角色名猜测；变更锁序与 D 签名一致 |
| C | 普通管理员任命、等级/范围/委派边界；恢复后资格检查；在联合批准的流程中限定可恢复对象和作用域 | 不把超级用户当普通组织等级、不把管理角色当任命；重审和重任命不扩大范围、不复活历史授权；普通接口仍拒绝超级角色 |
| D | 独立可信服务/恢复主体认证、请求权限与防重放、签名校验及密钥管理、恢复审计证据 | 篡改先保全与调查，不通过自动补签绕过；事实/最终签名/关键审计原子提交，证据可验证 |
| 集成负责人及 A/B/C/D | 确认受控入口、操作主体/审批和执行流程、初始自管数据、演练及失败处理 | 初始化成功一次、重复执行不造权限、误撤后受控恢复、签名故障不放行；记录共同验收证据 |

C 不新增万能超级用户 HTTP、硬编码超级用户 ID、普通 JWT 绕过、默认可用口令或可对任意旧数据补签的脚本。若只完成本次 C 规则，超级用户跨模块初始化/恢复和生产组织事件链路必须继续列为依赖阻塞。
